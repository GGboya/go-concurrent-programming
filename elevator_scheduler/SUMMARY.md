# 电梯调度系统总结

## 🎯 问题背景

小明对电梯的调度策略很感兴趣。当小明要回家上楼的时候，他会把两个客梯的按钮都按一下。与此同时，可能其他楼层也会按电梯，那电梯到底是怎么调度的呢？

## 🏗️ 系统架构

我们用Go语言实现了两个版本的电梯调度系统：

### 1. 基础版本 (`main.go`)
- **2部电梯**，10层楼
- **SCAN算法** + 最小成本分配
- 基本的并发控制和请求处理

### 2. 高级版本 (`advanced/main.go`)
- **2部电梯**，每部载客8人，10层楼
- **优先级SCAN算法** + 智能成本分配
- 载客量管理、优先级调度、实时监控

## 🔧 核心调度算法

### SCAN算法（电梯算法）
```
1. 电梯继续当前方向运行
2. 服务路径上的所有请求
3. 到达边界后改变方向
4. 重复上述过程
```

### 成本计算公式
```go
基础成本 = |当前楼层 - 请求楼层| × 10
方向惩罚 = 方向不一致 ? 50 : 0  (基础版本)
方向奖励 = 方向一致 ? ×0.7 : ×1.5  (高级版本)
队列成本 = 请求队列长度 × 5
载客成本 = 载客率 × 0.5  (仅高级版本)
优先级成本 = (11-优先级) / 10  (仅高级版本)
```

## 🚀 并发编程特性

### 1. Goroutine使用
- **每部电梯**运行在独立的goroutine中
- **调度器**的请求分发器运行在单独的goroutine中
- **状态监控器**运行在独立的goroutine中（高级版本）
- **模拟用户请求**使用goroutine异步生成

### 2. 同步机制
```go
// 互斥锁保护共享状态
mutex sync.RWMutex

// 通道用于goroutine间通信
requestChan   chan Request
passengerChan chan Passenger  // 仅高级版本
statusChan    chan ElevatorStatus  // 仅高级版本
stopChan      chan bool

// Select语句处理多个通道
select {
case req := <-e.requestChan:
    // 处理请求
case <-e.stopChan:
    // 停止电梯
default:
    // 处理现有请求
}
```

### 3. 线程安全设计
- **读写锁**：允许多个读操作并发进行
- **原子操作**：保证数据一致性
- **通道通信**：避免共享内存的竞态条件

## 📊 小明按电梯按钮的场景分析

### 场景描述
```go
// 小明在1楼，要上楼，按了两个电梯的按钮
scheduler.CallElevator(1, Up, 5) // 第一个按钮
scheduler.CallElevator(1, Up, 5) // 第二个按钮
```

### 调度过程

#### 1. 请求接收
```
🔔 请求 #1: 1楼 上行 (优先级: 5)
🔔 请求 #2: 1楼 上行 (优先级: 5)
```

#### 2. 电梯选择
调度器计算每部电梯的成本：
- **电梯1**：距离=0，队列=0，成本最低
- **电梯2**：距离=0，队列=0，成本相同

#### 3. 请求分配
```
🔔 电梯 1 收到请求：1楼 上行 (优先级: 5)
🔔 电梯 1 收到请求：1楼 上行 (优先级: 5)
```

#### 4. 请求处理
由于两个请求都是同一楼层，电梯1直接完成：
```
✅ 电梯 1 完成请求：1楼 上行 (等待时间: 0.2秒)
✅ 电梯 1 完成请求：1楼 上行 (等待时间: 0.2秒)
```

### 为什么两个请求都分配给了同一部电梯？

1. **成本相同**：两部电梯都在1楼，距离成本相同
2. **先到先得**：调度器按顺序评估电梯，电梯1先被选中
3. **效率优化**：同一楼层的请求由同一部电梯处理更高效
